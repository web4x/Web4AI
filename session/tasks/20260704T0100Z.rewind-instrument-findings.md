## FIX DELIVERED — oosh-expert (`7059a36`, origin/dev)
**Root cause**: `otmux.pane.capture` used `capture-pane -p -S "-${lines}"` — the `-S` reaches into the **scrollback buffer**. A bridged/relayed pane does NOT keep scrollback in sync with the live screen (the bridge relays the rendered visible frame; scrollback accumulates stale/partial frames or stays empty). So `-S -N | tail` returned stale/blank → composers looked "won't clear", menus "won't render", responses missed. `private.resolve.target` was NOT implicated (it passes a qualified `sess:win.pane` through unchanged).
**Fix**: capture the **VISIBLE screen** with `-p` (no `-S`) — exactly the canonical reliable `tmux capture-pane -p`. Strip trailing blank padding (interior blanks preserved), then `tail -N`. Off-screen scrollback stays available via `otmux pane.history`.
**Proven (local A/B)**: new logic == raw `capture-pane -p` content (prompt, `/rc active` footer, task list, interior blanks) — parity confirmed. The old `-S` form is the divergent/unreliable path.
**Tester**: live A/B over the WODA.prod bridge — `otmux pane.capture <bridged-pane> N` should now match `tmux capture-pane -t <pane> -p | grep -v '^blank'` (no blank/stale). Sibling send-verify captures (`send.verified` still use `-S`) are s2-g send-side territory — flagged, not in this read-side fix.
