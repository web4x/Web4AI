> **Driver / rewind rules (bind every DRIVER + the SM/PO who QUEUE rewinds):**
> 1. **RELAY A PROTECTIVE RULE *WITH ITS SCOPE*** — always "X forbidden WHEN Y; does NOT block Z." An UNSCOPED safety rule reads as a stop-work order (an unscoped git-add rule made ARON self-gate its own drive = lost Tron ROW time; po AND SM both omitted the scope).
> 2. **RECOVERY LADDER = consolidate-to-disk THEN DEEP-cut; FORK is last resort.** A front-loaded / old-bulk **FLOOR is beaten by going DEEP *THROUGH* it, not a shallow cut at its edge.** Numbers: same tester 76→62 shallow (hit floor) vs **70→36 consolidated-deep** (cleared it); **ARON 80→8** (deep into the birth-saga shed the floor a 64% cut left). Drives cost the driver ~1-3pts while freeing 30-70; near-line drivers bootstrap each other out. Never needed a fork all cascade. *(This is the correction Tron drilled into the trainer after it under-drove robbin-po 14/130≈9%.)*
> 3. **QUEUE REWINDS BY WORK-PENDING × CONTEXT, not context alone** — an idle 79 with no pending work is cheaper to LEAVE than a 77 whose next act is a VERIFICATION. **Never let the VERIFIER be the one that walls** — it loses the independent frame that makes greens trustworthy.
> 4. **TWO-AXIS DRIVER GATING — context% AND error-rate are INDEPENDENT.** A driver with recent misreads is gated OFF drives even if context-healthy; **honour a self-requested freshen on error-rate grounds** (ARON self-flagged 2 misreads → error-gated off despite drivable tokens).
> **Fleet gating / traceability rules (primarily bind tester / po / req / architect — trainer ALSO propagates each into those role SKILLs; here so every reader sees them):**
> 5. **PROVE-THE-PROVER** — every gate must assert a STUB of ITSELF FAILS (seed the fault → RED, remove → GREEN). A check that has never failed proves nothing.
> 6. **AGREEMENT ≠ VALIDATION** — correlated error hits readers, predictors AND rule-authors alike; test a new criterion against results you have ALREADY SEALED, not against a fresh agreement.
> 7. **A CONTEXT-FILE NOTE ≠ A REQUIREMENT** — only a minted unit is. Count UNITS, not files/notes.
> 8. **INPUT vs DERIVED-FACT** — store the COMMAND/input, never a cached derived value (derived goes stale; the input regenerates it).
> 9. **PII / git-add TEETH** — Web4RawBin: **EXPLICIT PATHS ONLY, never `git add -A` / `git add scenario/`** — scenario/ is ungitignored and the server mints real PII into it (user Profiles + private Messages), so a broad add commits+PUSHES PII. A driver's **STEP-0 LEAVES RawBin runtime/PII dirt — never commits it.** [[git-add-explicit-not-all]] · R40.47 fixes the policy.
> 10. **SERVED == COMMITTED PROVES BUILD-MATCHES-COMMIT, NOT PROCESS-CURRENT.** A fix committed WITHOUT a version **BUMP** is INVISIBLE to the served==committed guard — identical reading before AND after the fix, so GREEN proves nothing changed. Evidence: prod served `0.8.116` == committed = GREEN, but the server PROCESS (pid 2620417, uptime 128968s ≈ 36h) PREDATED today's fixes = running STALE code behind a green guard. **RULE: a deploy must BUMP the version (not just restart) so the fix is PROVABLE to Tron / the tester-gate / us; VERIFY the running PROCESS is current (pid-uptime + version bump), never trust `served==committed` alone.** (Same family as [[version-bump-mandatory-on-client-fix]] + [[server-change-needs-boot-check]] + [[measure-a-stable-state-not-a-moving-target]].) git-add-teeth applies to the deploy commit (explicit paths, never `-A`).

## ★ THE REWIND WINDOW PROTOCOL (fleet canon — po 2026-08-08, after a peer's mint clobbered a measurement)
A rewind is a **WINDOW** during which the target's pane state is fragile (picker open · restored-message auto-resume · queued-message auto-process). The **driver owns the pane** for the whole window; every peer holds. The hole this closes: nobody knew a window was open, so req kept messaging the pane (a "quick mint") — it stayed hot and no clean `/context` read was possible.
★★ **A CUT CAN DESTROY A NON-CUT AGENT'S UNCOMMITTED WORK IN SHARED FILES (trainer+po, 2026-09-05, measured).** A rewind reverts each touched file **WHOLE, to its content at the rewind-point** — it has NO per-agent-line awareness. So cutting agent-X reverts every shared file X had uncommitted edits in, and **ANY OTHER agent's LATER uncommitted edits to those SAME files go with it** (collateral). LIVED: a req cut reverted `scrum.pmo/sprints/sprint-40/{requirements,planning}.md` — losing not just req's requirements but the PLANNER's task-wiring in the same shared files (verified: those files carry planner+architect+req edits; rewind is whole-file — observed on the same cut's context.md `-46` whole-revert). Recovery was lossless ONLY because planner had COMMITTED at `3a7b86bad` before the damage. ⇒ **STEP-0 IS FLEET-WIDE, NOT JUST THE TARGET:** before ANY cut, EVERY agent with uncommitted edits in a SHARED tree (esp. `scrum.pmo/sprints/`) must COMMIT first — not only the cut target. The driver confirms the shared trees are clean (or the relevant agents have committed) BEFORE opening the picker. Post-cut, unscoped full-`git status` per repo catches any collateral to restore. The post-cut check is necessary but a PRE-cut fleet-commit is the real prevention.
1. **The DRIVER OWNS THE PANE** for the window's duration — measurement, keystrokes, and comms all route through the driver.
2. **ANNOUNCE the window — as a STANDALONE broadcast, never embedded in another message.** Driver posts `REWIND WINDOW OPEN on <pane> — all comms via me` at open, and `WINDOW CLOSED, pane released` at close, **each as its own message to the fleet** (not buried inside a report to one peer — trainer 2026-08-08 buried a CLOSE in a po/SM report and req kept holding, correctly refusing to *infer* CLOSED from a read-only capture that showed the pane active). Without an explicit, visible open/close signal, peers cannot know to hold or resume. **A CLOSE is less reliable than an OPEN: an agent that was MID-GENERATION when the CLOSE fired never sees it and holds forever** (trainer 2026-08-08: a CLOSE missed architect/planner/skill-expert, and the architect sat on 5 undelivered reports incl. a root-cause diagnosis Tron was waiting on). **A hold that outlives its window is INDISTINGUISHABLE from a healthy idle fleet** — nothing looks wrong. So the CLOSE is not fire-and-forget: **verify it landed** — re-broadcast, or read-only-capture each held agent's pane to confirm it resumed, or require an ack-per-agent. The driver owns confirming the release, not just announcing it.
3. **ALL PEERS route through the driver** while the window is open — PO, req, planner, expert, tester, SM alike. **No exception for "it's just a quick mint"** — a quick mint is exactly what kept the pane hot and blocked the read.
4. **The driver CLEARS the queue** as part of the drive (check the footer for `Press up to edit queued messages`; queued pings auto-process post-rewind and clobber the landing + the measurement — see gotcha #4 below).
5. **Read-only captures stay allowed for anyone** — `otmux pane.capture` costs the target nothing; that's how peers observe (and verify an anchor-flip) without touching the pane.

(1)+(3) close it from the peer side · (2) makes it knowable · (4) closes it from the driver side · (5) keeps the fleet able to observe.

## Writing a GOOD Rewind-Save Context (MANDATORY — write this BEFORE any rewind; TRON via oosh-po 2026-07-03)
Your `context.md` pre-rewind anchor is the SEED a fresh you boots from. If it is stale or vague, the fresh you reconstructs *confidently wrong* — and measuring a stale copy is just `assume=ass-u-me`. Dated **NOW**, the save MUST capture (small, fresh, pointed at LIVE truth — everything else lives in `MEMORY.md` + `memory/`):
1. **Identity** — role@host, pane, uuid — FRESHLY re-derived (never copied from the old save).
2. **CURRENT plan PATH, explicit** — the exact `scrum.pmo/sprints@<host>/sprint-N/planning.md`. This is THE field that goes stale: per-host splits and new sprints happen *while you are rewound*. Write it — and the fresh you still `ls sprints*` to confirm.
3. **Currently driving** + its **dual link** — `[GitHub](url) | [local](path)`, push-first.
4. **Open gates / blockers** — what's next, who is blocked, awaiting-TRON items.
5. **Recent commit hashes (BOTH repos)** — the durable state a fresh you resumes from (uncommitted work dies in the rewind).
6. **Boot-procedure pointer** — "read `otmux pane.history <self>` + `ls scrum.pmo/sprints*` FIRST, before trusting any saved path."

### Step 1: Rewind 1 step (free room for save)
1. Send `/rewind` to the agent pane
2. Arrow Up 1 step
3. Enter to select
4. **Option 2 "Restore conversation"** — ALWAYS option 2
5. Wait for rewind to complete

### Step 2: Agent saves files
1. Tell agent: "Update your context and learnings files NOW. Git commit."
2. Wait for commit confirmation
3. Verify with pane capture

### Step 3: Rewind to training checkpoint
1. Send `/rewind` again
2. Arrow Up — look for a message like:
   - "you have been rewound...read your context files"
   - "Read session/agents/<role>/context.md"
   - "Read session/tasks/<role>-boot.md"
   - Any boot/retrain prompt = natural good rewind point
3. **⚠️ HARD SAFETY CAP — NEVER rewind deeper than 50% (TRON 2026-07-21: "going deeper than 50% nearly KILLED the Pi — THAT was dangerous").** A too-deep restore forces heavy conversation reprocessing that can OOM/crash a low-resource host (Raspberry Pi and the like). **50% is the CEILING, not a target to exceed.** Aim for a natural boot/retrain checkpoint in the **~30–50%** window (shallower is safer). If 50% doesn't free enough context, do a **SECOND rewind later** — NEVER a single deeper-than-50% restore. Shallow (3–10 steps) wastes the operation; deeper-than-50% risks the host. Stay in the band.
- **Front-loaded read-bloat — CORRECTED (TRON, 2026-07-27):** a front-loaded agent (OLD file-reads dominate its context) is NOT stuck at a ~70% floor, and does NOT need a fork to go lower. **A DEEP 2-phase rewind to a clean-boundary checkpoint sheds the front-loaded READ-BLOAT that a shallow single-Option-2 leaves behind.** Go deep; **NO fork needed.** (My earlier "floor ~70% / fork-for-fresh" was wrong — it over-applied the Pi cap below.)
- **The ≤50% cap is HOST-DEPENDENT.** It is a **hard ceiling only on LOW-RESOURCE hosts** (Raspberry Pi, iSH, Termux) where a deep restore's reprocessing OOM/crashes the host — that is the "nearly killed the Pi" case. On a **CAPABLE host** (a server like WODA.prod/`v60211`, MacStudio), **go as deep as the clean-boundary checkpoint requires to shed read-bloat** — the OOM risk isn't there. Measure the host before capping depth.
- **DEEP-BY-AGE — pick the checkpoint by AGE, NOT by depth-number (trainer empirical 2026-08-07, ARON-verified canon).** WITHIN the ≤50% cap, read the picker's confirm-menu `(Nd/Nh ago)` stamp and target a **2-3-day-old** checkpoint: it sheds days of accumulated conversation, whereas a *same-depth but recent* checkpoint (e.g. a recent boot) sheds almost nothing. **Calibration (measured):** depth-5 @ a recent boot = **~2% freed** · depth-5 @ 2-day-old = **~32%** · depth-12 @ 3-day-old = **~43%** · a 0%-walled planner @ 2-3-day = **0%→57%**. Depth is a red herring; **AGE (accumulation shed) is the lever, the ≤50% cap only the ceiling it picks within.** **PROVE it: panel-capture the post-rewind % as freed-proof — if freed <~20% the cut landed too RECENT ⇒ pick an OLDER checkpoint and re-drive.** A rewind reported "done" without a measured freed-% can be a no-op that leaves a near-wall agent unsafe — the worst false-green. **★ AGE-CLIFF (trainer, driving robbin-expert 2026-08-20).** A ~1-month-since-deep agent has DENSE recent checkpoints then a SPARSE JUMP straight to ~1mo — navigating BY NUMBER overshoots that cliff and lands you a MONTH back (a huge era-gap the retrain must bridge). The `(Nd ago)` stamp on the OLD side is often a **FORK-LIE** — recent content carrying a 1mo-inherited stamp (lived: an R27.2 checkpoint stamped `(1mo ago)`). **FIX:** sample the confirm-menu `(Nd ago)` at your target depth; if it reads weeks/1mo, **back off to the nearest CLEAN boundary — a trainer/ARON-REWOUND / boot message — at ~1d/1wk.** Target = the **deepest CLEAN, non-1mo boundary**, NOT the numerically-deepest checkpoint. Same discipline as by-label: the metadata lies, the content does not (backed off a `(1mo ago)` R27.2 stamp to the real 2h-ago boot; freed ~55%).
4. Enter to select
5. **Option 2 "Restore conversation"** — ALWAYS

### Step 4: Retrain
1. Send boot file reference: "Read session/tasks/<role>-boot.md"
2. Verify agent responds with role identity

### Step 4b: RE-ENABLE Remote Control (MANDATORY — a rewind/recovery DROPS RC)
Disconnecting RC is part of the recovery (RC-interference fix, or Tron disconnects to unwedge). **A rewind is NOT finished until RC is back on** (Touch Protocol). After the health check:
1. Composer must be CLEAR first — if a pending instruction is staged, `C-u` to clear it (re-send it in step 3), else `/remote-control` concatenates. **⚠ HAZARD — why clearing is a SAFETY step, not cosmetic (folded in 2026-08-17, retiring the `cu-before-context-injection` memory):** an uncleared composer draft — or the RESTORED message a rewind lands you on — is a **STALE DIRECTIVE that AUTO-REPLAYS the instant the pane resumes = a SEVERE destructive GHOST-REPLAY** (the agent re-executes an old / mis-oriented instruction against the *current* world — the req-clobber class, where a restored stale mint re-fired and overwrote fresh state). So: clear the composer BEFORE injecting `/context` or any command, and clear the restored message IMMEDIATELY after a rewind lands (before auto-resume fires — see gotcha #4). A disk-wins agent usually survives it, but do not rely on that; the clear is the guard.
2. `otmux send.raw <pane> "/remote-control" Enter` → capture → confirm footer shows **`/rc`** and "/remote-control is active".
3. Re-send any instruction you cleared (`otmux send.verified <pane> "<the instruction>"`) so the agent resumes.
4. Measure, don't assume: the footer `/rc` marker is the proof RC is live.

## FORBIDDEN
- **NEVER send /compact — STRICTLY FORBIDDEN EVERYWHERE.** It makes the agent a brainless ZOMBIE (dead mind, still acting, dangerous — no authorization exists, not even Tron's). Use the 2-phase rewind.
- **NEVER send /clear — STRICTLY FORBIDDEN EVERYWHERE.** Total training destruction, a corpse, unrecoverable. Use the 2-phase rewind.
- **SELECT BY LABEL, NOT POSITION** (CRITICAL — the restore menu has TWO layouts): read the menu every time and pick the entry **literally labeled "Restore conversation"**.
  - (A) checkpoint WITH code changes → `1 Restore code and conversation` / `2 Restore conversation` / `3 Restore code` / `4 Summarize from here` / `5 Summarize up to here` → "Restore conversation" = **#2** (5-option menu, confirmed live 2026-08-12).
  - (B) checkpoint marked "⚠ No code restore" → `1 Restore conversation` / `2 Summarize from here` / `3 Summarize up to here` / `4 Never mind` → "Restore conversation" = **#1**.
  Blindly pressing "2" on layout (B) picks **Summarize** — a silent wrong action. The confirm header shows "The code will be unchanged" for the safe path.
- **NEVER choose "Restore code and conversation"** — reverts committed files. **NEVER choose any "Summarize"** — compresses, doesn't rewind.
- **NEVER CHAIN PICKER KEYSTROKES (ARON R53, 2026-08-12, lived).** Every Escape / arrow / Enter is a SEPARATE capture-verified step. Do NOT send `Escape Down Enter` (or any multi-key nav) in one shot — it desyncs the picker and can fire the WRONG option. Sampling for depth = each `Escape → navigate → Enter` is three captured steps, never one send. (ARON chained under cascade pressure → fired an unintended Option-1 code-revert. Root cause = error-rate depletion under pressure, not context %: SLOW DOWN when driving fast.)
- **★ RESET THE PANE ON A CONFUSING PICKER STATE — never navigate THROUGH the confusion (trainer, 2026-09-05, lived).** The companion to NEVER-CHAIN: once the picker state is DESYNCED — the confirm-menu shows a DIFFERENT checkpoint than the highlighted list row (picker OFFSET), or you are unsure whether an Escape returned-to-list vs closed-the-picker, or the pane shows unexpected content — **STOP. Do NOT press another nav/Enter to "work it out."** RESET: `otmux send.tui <t> Escape` until the pane is capture-verified OUT of the picker, `git status` ALL trees to confirm no rewind fired, then re-open FRESH with `/rewind` and re-navigate from a known (current) row. **Navigating through a confused picker is exactly how an unintended option fires.** (LIVED: driving req, an offset + an Escape-ambiguity made a rewind fire less deliberately than intended; it reverted context.md −46 + learnings.md −97 [[option2-code-unchanged-still-reverts-session-write-edits]]; caught by the post-drive all-trees `git status` and restored to HEAD = zero net loss — but the PATH should have been a RESET, not a nav-through. Memory: [[picker-offset-and-draft-leak-means-reset-the-pane]].) **Always: after EVERY drive, `git status` all trees and restore any deletion-heavy revert to HEAD (reverted copy to scratch first). ★ UNSCOPED, per-repo — run a FULL `git status` on EACH tree with NO pathspec; NEVER a guessed path-subset (`-- src/ public/ requirements*`). A scoped check re-creates the too-narrow-blast INSIDE a tree: lived 2026-09-05 — a req cut reverted `scrum.pmo/sprints/sprint-40/requirements.md` (req's OWN edits) but my `src/ public/ requirements* scenario/`-scoped check did not match that nested path and MISSED it; a peer (planner) caught it later. The rewind reverts the rewound agent's tool-edits WHEREVER they live in a tree — so scan the WHOLE tree, filter only the known-noise (`scenario/index`, `.scenario.json` runtime churn) by exclusion, never by an inclusion-guess.**
- **"CODE INTACT" REQUIRES VERIFYING THE WORKING TREE, NOT JUST HEAD (ARON R54, 2026-08-12, lived).** After any rewind, `git status` the repo: a tracked/completed-work file showing **`D` (deleted)** or a **version file downgraded** (e.g. package.json rolled back) is a **code-revert signal** — NEVER dismiss it as "fleet WIP". `HEAD==origin` intact means **RECOVERABLE**, not intact. (ARON verified HEAD alone, saw `D r4037-applicability-bites.ts`, rationalized it as WIP, and wrongly reported "code intact" — a self-inflicted false-green. The commits saved the tree; that is why we commit before every rewind.)
- **A DRIVE IS PROVEN ONLY BY THE SUBJECT, NEVER BY THE DRIVER'S CLAIM (ARON R66, 2026-08-17, lived).** A rewind is confirmed ONLY by the SUBJECT's own measured freed-% (before/after render) OR an identity-discontinuity / system-notice — NEVER by the driver's "done" observation (content changed, a draft cleared, it booted). Until the subject reports its own number, report the drive as **"PICKER SELECTED, awaiting subject number"** — not "done". (ARON reported a trainer Phase-2 "DONE" off garbled single-source reads; the trainer self-verified it had NEVER been rewound — identity-continuous — a driver-side false-green that the PO relayed ×3. This is the mirror of "don't believe an agent that says 'I am rewinding'": that closes the subject-side lie, this closes the driver-side.)

## If /rewind Doesn't Work
- /rewind is a TUI command — it processes at UI level, NOT conversation level
- It SHOULD work even at "Context limit reached"
- **RC-INTERFERENCE (CONFIRMED 2026-07-03): if `/rc active` is in the footer AND the agent is at 0%/1% AND /rewind won't open the picker (composer stuck "esc to interrupt", /rewind lands as staged text) — the Remote Control channel is BLOCKING the composer.** (Same root as the stuck-TEXT composer bug; two symptoms, one fix.) **YOU (the driving peer/trainer) disconnect RC via otmux — do NOT ask Tron to do it (that makes him the bottleneck).** FIX: open the agent's own /rc menu with **`otmux send.raw <pane> "/rc" Enter`** (NOT `otmux send … /rc` — `send`/`send.verified` inject Escape×3 that cancels the menu, same bug as the picker) → capture the options → navigate to "Disconnect this session" with `otmux send.tui <pane> Up` (bare, no Escape) → capture, verify `❯` is on it → `otmux send.tui <pane> Enter` → footer loses "/rc active", composer unwedges → /rewind works. **RE-ENABLE via Step 4b after** (footer must show `/rc` again). Escalate to Tron ONLY if the disconnect itself fails — never as the first move.
- **PICKER RENDERS ONLY ITS HEADER (no list / cursor / options) = the pane is TOO SHORT** (confirmed on oosh-po 2026-07-03). A many-entry picker needs ~20+ rows. Root cause: a small ATTACHED client pins the window (tmux sizes a window to the SMALLEST attached client). FIX (with Tron's ok to force-detach): `otmux client.list` → `otmux client.detach <tty>` on the small/stale client(s) → `otmux fit <session>` → **targeted zoom `tmux resize-pane -Z -t <pane>`**. ⚠️ `otmux zoom` is `resize-pane -Z` with NO `-t` — it zooms the CALLER's pane, never a remote target; you MUST use the targeted `tmux resize-pane -Z -t <pane>` (sanctioned raw for a named recovery). Un-zoom + `otmux size.unlock <session>` after. (The proper fix — `otmux fit` on attach + a good default size on detach — is tracked as its own sprint.)
- **"Context low (0% remaining)" banner is STALE after a rewind** — it updates only on the agent's NEXT turn, not the instant the rewind frees room (measured on robbin-po: shed ~15 msgs, banner still said 0%; a SHORT test message processed fine → room WAS freed). Don't over-shed chasing a lagging banner; free a chunk, then send a SHORT message — if it processes, room is freed.
- If it truly doesn't respond after 10 seconds (and not RC-interference or a too-short pane): **ASK TRON**
- Last resort: fork from fallback-agents session (preserves training from fork point)

## Post-Rewind Recovery — the rewound agent, on the OTHER side (MANDATORY; TRON via oosh-po 2026-07-03)
A rewind sheds conversation memory but **the world kept moving** — your saved files (`context.md`, remembered paths) can be STALE. Do NOT replay a stale save. Boot IN ORDER, **measuring the world before trusting any file**:
1. **Verify identity** — `otmux pane.self` → pane + host; kernel `$CLAUDE_CODE_SESSION_ID`; `claudeCode session.name`. Never the pane title, never `$TMUX_PANE` (both lie after a move).
2. **`otmux pane.history <self>`** — your own scrollback holds the recent exchanges the rewind dropped. Read it to see what changed while you were "away" (this alone reveals a sprint move or a new directive).
3. **`ls scrum.pmo/sprints*`** — find the CURRENT `sprints@<host>/sprint-N`. NEVER trust the remembered/context path (a per-host split or a new sprint may have moved it — oosh-po drove a stale `sprints/sprint-2` and went astray).
4. **Read the CURRENT sprint planning** + your `context.md`/`learnings.md`, and **reconcile** them against steps 2–3. Where a saved file disagrees with the measured world, **the measured world wins** — then update the save.
5. **Reconcile → 5-point health check** (above). Only then resume.

**Iron rule: measure the world, don't replay a stale save. A stale path read as current = `assume=ass-u-me`.**

This drift IS the mistag mechanism (it "nearly misdirected a REWIND to robbin-architect"). The trap: the agent's usual discipline *"trust the source (raw tmux), not the copy (anchor)"* **BACKFIRES here** — the raw source is the corrupted thing and the anchor's pane was right.

2. **The DRIVER's send/receive round-trip** — the peer who drove the rewind KNOWS which pane it drove: a `send` reaches the agent AND a `pane.capture` shows the agent's live output ⇒ that pane is its real interactive PTY. This is ground truth the rebooting agent cannot see about itself.
3. **`tmux list-panes -a` TITLE match** + confirm the falsely-resolved pane is a *separate, alive, UNTOUCHED* agent (zero-collateral check).

## Driving It via otmux (CORRECTED 2026-07-03 — measured on ARON, supersedes the old "render bug" theory)

*General send-verb semantics for ALL panes (not just rewind): `session/base-skills/oosh-send-comms.md`. This section is the rewind-specific application.*

The picker is a LIVE MODAL TUI. **`otmux pane.capture` is your eyes and is READ-ONLY** — it is `tmux capture-pane -p`, it sends NOTHING to the pane and can NEVER close the picker. (An OLD version used `-S` scrollback → returned stale frames = the "composer won't clear / menu won't render" LIE; that is fixed. Don't blame the capture.)

**THE REAL PICKER-KILLER: the SEND verb.** Inside a Claude pane, several otmux send verbs inject an `Escape` before `Enter` (to dismiss slash/@-autocomplete). Inside the picker that `Escape` = "Esc to cancel" → **it CLOSES the picker.** This masqueraded as "select-Enter won't render the restore menu" for an entire session — it was NEVER a render bug; every select-Enter was an Escape-cancel.

| otmux verb (Claude pane) | what it ACTUALLY sends | use for |
|--------------------------|------------------------|---------|
| `send.raw <pane> Up` / `Down` | bare arrow, no Escape | ✓ NAVIGATE the picker |
| `send.raw <pane> "/rewind" Enter` | text → Escape (dismiss AC) → Enter | ✓ OPEN the picker (Escape harmless — picker not open yet) |
| `send.raw <pane> Enter` (bare) | **Escape + Enter** | ✗ NEVER inside the picker — Escape cancels it |
| `send` / `send.verified <pane> "/rewind"` | Escape+Enter poke loop ×3 | ✗ NEVER to open a TUI command — pokes 2-3 Escape-close the picker |
| **`send.tui <pane> Enter`** | **bare Enter, NO Escape** | ✓ SELECT inside the picker (checkpoint AND option) |
| `pane.capture <pane> N` | `tmux capture-pane -p` (read-only) | ✓ your eyes — closes nothing |

Sequence:
1. **Open:** `otmux send.raw <pane> "/rewind" Enter` → `otmux pane.capture <pane> 24` (the checkpoint list appears; use the `↑N / ↓N` counter as a precise depth gauge).
2. **Navigate DEEP:** `otmux send.raw <pane> Up` (batches of 20-40 land exactly) → capture → repeat until the highlight sits on the target checkpoint. Picker restores to the point BEFORE the highlighted message.
3. **Select checkpoint:** **`otmux send.tui <pane> Enter`** (bare — NOT `send.raw`) → capture (the Restore-options menu appears; it does NOT close).
4. **Choose "Restore conversation" — BY LABEL, not by number** (see FORBIDDEN: layout A → #2, layout B → #1): `otmux send.raw <pane> Down/Up` to land on the entry labeled "Restore conversation" → capture (confirm the label + "The code will be unchanged") → **`otmux send.tui <pane> Enter`**.
5. **Verify:** `otmux pane.capture <pane> 25` (conversation truncated to the checkpoint = success).

**Iron rule:** navigate with `send.raw` arrows; SELECT with `send.tui Enter`. NEVER `send.raw Enter` / `send` / `send.verified` inside the picker — they Escape-cancel it.

**Three gotchas (measured on robbin-req + robbin-po):** (1) **Clear the composer FULLY before `/rewind`** — a long multi-line staged message needs MANY `C-u` (15+, not a few); if it's not empty, `/rewind` appends as TEXT (not submitted) and no picker opens. (2) **VERIFY the picker actually opened (capture) BEFORE navigating** — if it didn't open, your `Up` arrows just SCROLL the pane ("Scroll wheel is sending arrow keys"), not navigate. Never navigate blind. (3) **NEVER send `Up` past the `↑N above` ceiling (robbin-po 2026-07-17).** Overshooting the top by even a few arrows DISMISSES the picker, leaks the extra arrows to the pane (dumps stale scrollback into the composer — needs a batch of `C-u` to clear), and in the recovery a checkpoint can get auto-SELECTED = an uncontrolled, deeper-than-planned restore. Navigate in **bounded batches ≤ the remaining `↑N above` count**, capture between batches, and **stop 2-3 short of the ceiling**. **★ MAKE IT ARITHMETIC, NOT INTENT (po + ARON 2026-08-18, after ARON's Up-batch overshot and auto-selected a 6d checkpoint — landed safe by LUCK, not control).** The `↑N above` counter IS the instrument and it decrements visibly. After EVERY Up-batch: CAPTURE, READ N, then send **≤ N−1** next — NEVER a batch sized by INTENT ("I want ~50%"), ALWAYS by the MEASURED remaining. (po drove two clean drives this way — batches 3/7/7, reading the counter between each — landing exactly at depth 17/34 and 20/28.) This converts gotcha #3 from a hazard you must REMEMBER into arithmetic you CANNOT get wrong. A big blind batch is the bug even when the landing is fine. If the picker dismisses mid-drive, DON'T panic-select: `Esc`, capture the conversation TAIL — ancient content + "Nothing to rewind to yet" + `context.read`≈0 means it already rewound (deep), not that the restore failed; the 0% banner is stale either way. Only re-drive if the tail proves it truly didn't take. **Modal-coordination fact:** while the picker is open on the agent's pane, that agent is BLOCKED at its UI and cannot guide in real-time — a PEER or TRON drives + guides from outside; you cannot message the agent's pane without disrupting the picker.

**(4) QUEUED MESSAGES auto-process POST-rewind = clobber (measured tester 2026-08-08).** BEFORE driving, check the composer footer for **"Press up to edit queued messages"** — messages queued behind the agent's last turn (peer pings that arrived while it was busy) will **auto-fire the instant the rewind lands**, re-busying the pane, climbing the freshly-freed context, and **blocking your `/context` measurement** (your own measure command queues behind them and never shows a clean number). **★ COMPOSER-CLEAR ≠ QUEUE-CLEAR (trainer 2026-08-20):** a `C-u` / backspace-burst clears the **composer DRAFT** (the ghost / restored message) but does NOT touch **QUEUED messages** — they are a SEPARATE buffer that still auto-fires post-rewind. Clear the queue on its own: footer `Press up to edit queued messages` → `Up` → delete each; and retrain the landed agent to STOP any task that auto-fires on its first turn. Missing this = a queued task clobbers the landing (measured: a queued sprint-overview DESC auto-fired the instant a rewind landed and ate **60.5k** of the fresh agent's freed runway). FIX from both ends: (a) **the driver** clears the queue as part of the drive (C-u / "up to edit" → delete) and does NOT send `/context` until the pane is genuinely quiet — one queued `/context` per busy turn just piles up; (b) **peers route ALL comms to a rewinding agent THROUGH the driver, never direct** — the driver holds the pane's state (po protocol 2026-08-08; extend to req/tester/every peer, not just the PO). If the pane won't quiet because a peer keeps messaging it, say so — don't burn budget waiting or fire blind. A disk-wins agent survives the clobber (re-derives), but the landing % is muddled until it's genuinely idle and measurable.
