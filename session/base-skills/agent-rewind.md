> ## ★★★ THE TWO-PHASE LAW (TRON 2026-08-17 — CMM3/CMM4, NON-NEGOTIABLE, precondition for every role)
> - **PHASE 1 = the agent writes ITS OWN `context.md` + `learnings.md`. NON-DELEGABLE — no peer writes them for you.** A peer consolidating your files is covering your failure and HIDES the defect; post-wall your learnings are LOST and unreconstructable. **Write your own files at clean boundaries, CONTINUOUSLY**, so Phase 1 is already-done before any rewind is needed.
> - **The POINT of context-watching = GUARANTEE Phase 1 happens BEFORE THE WALL** — not to schedule a rescue, and NOT to pile more observers onto the drive. If an agent is climbing, flag it to *write-and-save* before it walls. That is the whole job of the watch.
> - **PHASE 2 (the drive) is RELATIVELY TRIVIAL + delegable** — a peer drives the picker. But **there is NO emergency deviation from the trivial DEFINED process** (no "skip Phase 1" emergency — that is exactly what floors a rewind high). Don't dramatise the drive; follow the steps.
> - **CMM3/CMM4 = the steps are DEFINED IN THIS SKILL and MEASURED, because Claude Code CHANGES ITS MENUS.** Folklore breaks on the next picker change → **SELECT BY LABEL not by number** (a menu reorder must never silently pick "restore code"), **CAPTURE between keystrokes**, and **PROVE the freed-% by render**. > - **⭐ WALLED-AGENT BRANCH (TRON 2026-08-17, correcting po's write-off of a walled planner's learnings).** A walled (0% / "Context limit reached") agent has **NOT** lost its recent learnings — **"0%" means CANNOT-ACT-RIGHT-NOW, not terminal**, and **depth is a DIAL whose FIRST use is buying back the ability to RECORD.** This does NOT contradict "no skip-Phase-1" above — it is how you HONOR non-delegable Phase 1 when the agent can't currently act. Order, NON-negotiable: **(a) SHALLOW rewind — 3-5 checkpoints ONLY** (just enough headroom to make it able to act; NOT recent-deep, NOT deepest — a deep cut FIRST would DISCARD the very turns whose learnings you are saving); **(b) the agent writes its OWN Phase 1** (still non-delegable — the shallow cut exists precisely to restore that ability); **(c) THEN the DEEP Phase 2** + hand fresh-it the undone work. Same method reads a too-short pane's `/context` Free-space line. Full method: `session/base-skills/context-measurement.md`.
> **⚠️ `pane.size.set` CLAMPS if you request a height > the window's rows — measure the window FIRST, then request a FITTING height (ARON 2026-08-12; first mis-diagnosed as a "pinned-window SPOF", then MEASURED and corrected).** In a many-pane window each pane is small (e.g. 83×21 as 1-of-8) but the WINDOW is usually full-size. `pane.size.set <pane> 90 46` **failed only because 46 > the window's 45 rows** — NOT because of a "small pinning client" (measured: the client was 194×45, large). A **fitting** height works: `pane.size.set <pane> 90 34` gave a 34-row pane (proven live), which renders the picker fine (needs ~20+). **Procedure:** `otmux client.list` → read the window/client size → request height ≤ (window rows − ~7 for the other panes) → verify with `otmux pane.size` BEFORE opening the picker → drive → restore. **There is NO pinned-window SPOF and NO `pane.present` capability is needed** — the earlier "un-pin the window / owed sprint" was an `ass-u-me` (a failed enlarge diagnosed without measuring WHY). Lesson: when an OOSH call "doesn't take", **measure the constraint** (window height, client size) before concluding a gap.
> **⚠️ THIRD render-blocker root cause — `window-size manual` (ARON discovered driving the trainer; trainer PROVED the fix live, 2026-08-12, baseTeam).** A window can be pinned SMALL by **`window-size manual`** INDEPENDENT of client size: baseTeam was ~56 wide though its client was 194×45, so its 2nd pane squished to **`1×31`** — which cannot render a picker AT ALL = a REAL block on that agent's (the SM's) future rewind. **Detect:** `otmux pane.size <pane>` shows a sliver (e.g. `1x31`); `tmux show-options -w -t <session> window-size` = `manual`. **FIX (reversible): `tmux resize-window -t <session>:<win> -x 194 -y 45`** — grow the manually-sized window to the client size → panes redistribute (the SM pane went `1x31` → `69x37`, proven) → picker fits. This is a THIRD, DISTINCT root cause: NOT the smallest-client-pin (below, fix=`client.detach`) and NOT the `pane.size.set` height-clamp (above, fix=fitting-height). So "no pinned-window SPOF" holds for the CLIENT-pin theory, but a `window-size manual` pin is real and separate. Restore the window size after if it was intentional.

## ★ THE REWIND WINDOW PROTOCOL (fleet canon — po 2026-08-08, after a peer's mint clobbered a measurement)
A rewind is a **WINDOW** during which the target's pane state is fragile (picker open · restored-message auto-resume · queued-message auto-process). The **driver owns the pane** for the whole window; every peer holds. The hole this closes: nobody knew a window was open, so req kept messaging the pane (a "quick mint") — it stayed hot and no clean `/context` read was possible.
1. **The DRIVER OWNS THE PANE** for the window's duration — measurement, keystrokes, and comms all route through the driver.
2. **ANNOUNCE the window — as a STANDALONE broadcast, never embedded in another message.** Driver posts `REWIND WINDOW OPEN on <pane> — all comms via me` at open, and `WINDOW CLOSED, pane released` at close, **each as its own message to the fleet** (not buried inside a report to one peer — trainer 2026-08-08 buried a CLOSE in a po/SM report and req kept holding, correctly refusing to *infer* CLOSED from a read-only capture that showed the pane active). Without an explicit, visible open/close signal, peers cannot know to hold or resume. **A CLOSE is less reliable than an OPEN: an agent that was MID-GENERATION when the CLOSE fired never sees it and holds forever** (trainer 2026-08-08: a CLOSE missed architect/planner/skill-expert, and the architect sat on 5 undelivered reports incl. a root-cause diagnosis Tron was waiting on). **A hold that outlives its window is INDISTINGUISHABLE from a healthy idle fleet** — nothing looks wrong. So the CLOSE is not fire-and-forget: **verify it landed** — re-broadcast, or read-only-capture each held agent's pane to confirm it resumed, or require an ack-per-agent. The driver owns confirming the release, not just announcing it.
3. **ALL PEERS route through the driver** while the window is open — PO, req, planner, expert, tester, SM alike. **No exception for "it's just a quick mint"** — a quick mint is exactly what kept the pane hot and blocked the read.
4. **The driver CLEARS the queue** as part of the drive (check the footer for `Press up to edit queued messages`; queued pings auto-process post-rewind and clobber the landing + the measurement — see gotcha #4 below).
5. **Read-only captures stay allowed for anyone** — `otmux pane.capture` costs the target nothing; that's how peers observe (and verify an anchor-flip) without touching the pane.

(1)+(3) close it from the peer side · (2) makes it knowable · (4) closes it from the driver side · (5) keeps the fleet able to observe.

## ★ THE BUILDER PAUSES AT EVERY LANDING (po/SM 2026-08-08, after the expert walled to 96% unnoticed)
Root cause of that emergency: **the busiest agent is the least measurable — which is exactly backwards.** An actively-building agent driven back-to-back (R40.1 → R40.2 → deploy → fix → re-root → CLI, no gaps) never reaches an idle boundary, and authoritative `/context` REQUIRES idle — so the back-to-back dispatch itself eliminates the only measurement window, and the builder walls silently.
- **THE BUILDER PAUSES AT EVERY LANDING** — the actively-building agent goes IDLE for one measurement after each landed unit (requirement / deploy / fix) BEFORE receiving the next item. A measurable boundary is created BY PROTOCOL, not by luck.
- **PRE-DISPATCH MEASUREMENT of the active builder is MANDATORY, and the gate may REFUSE the PO** — measure the builder (self or via SM/driver) before handing the next unit; if it's near-wall, route a rewind instead of the next unit. "I have no fresh number" on a builder about to receive work is a STOP, not caution.
- Monitoring is not optional: SM-on-monitor-only-without-proactive-sweep + a PO that dispatches without the pre-gate = the builder climbs unwatched. Measure the builder EVERY sweep.

## 🌙 AUTONOMOUS OVERNIGHT REWIND PROTOCOL (TRON 2026-07-21 — must run WITHOUT TRON)
The overnight fleet self-heals without waking TRON. Every autonomous rewind MUST pass this gate, IN ORDER — the driver runs it solo; a peer/SM **dispatch is a trigger, NEVER a substitute for these checks**:
1. **IDLE-check** — `otmux pane.capture <target>`: a spinner (Kneading/Brewing/Churning…) = **SKIP** (never interrupt a working agent). Drive ONLY an idle (empty `❯`) or walled agent.
2. **MEASURE — fresh, first-hand, NEVER a relayed claim.** Trigger `/context` on the target and read the **Free-space header yourself**. A peer/SM saying "it's at 1%" is NOT truth (the SM sent **3 FALSE "walled" alarms on a measurably-healthy agent, 2026-07-21**). Measure, or do not drive. **The `Context low N% remaining` pane BANNER is NOT authoritative either — it can be STALE/lagging** (trainer 2026-08-08: read a persistent "Context low 1-2%" on a po that a clean `/context` showed at **79%**, and emergency-drove a needless shallow rewind on the banner before measuring). **If the pane is too BUSY to ever idle for a clean `/context`, that is a reason to enforce a fleet-HOLD and WAIT for genuine idle — NOT to interrupt-and-drive on the banner.** A busy pane also runs a queue-loop that makes the picker pathologically flaky (dismisses mid-nav); the fleet-hold quiets it and the picker stabilizes.
3. **THRESHOLD + MEASURE-THEN-DECIDE (TRON 2026-07-23)** — drive only if measured usage is **≥85% used (≤15% free)**. Proactive, before the cliff. Below that → leave it working (NEVER-FREEZE — don't park a healthy agent). **A peer FLAG is a trigger to MEASURE, not an order to rewind.** Measure fresh, then decide: if the agent is **not-near-wall (real runway, e.g. 370k free)** AND **weekly-budget-scarce** (near its per-account weekly cap — a context-rewind does NOT refill weekly budget), **let it RIDE** — rewinding spends scarce budget for marginal gain. Rewind only when the context wall is actually near. (Known weekly-scarce: tester, trainer.) **CONTEXT-WALL and WEEKLY-LIMIT are DIFFERENT constraints with OPPOSITE remedies, and an agent can hit BOTH at once (po 2026-08-08: req was 98% context AND 89% weekly).** Their pane banners look alike at a glance — `Context low N% remaining` (rewind fixes) vs `N% weekly limit, resets <date>` (rewind CANNOT fix, and re-reading the context SPENDS weekly budget). **Read WHICH it is, and identify BOTH.** If context-walled → rewind; then, if also weekly-scarce, **LOAD THAT AGENT LIGHTLY** afterward (a freshly-rewound agent with 426k context but 11% weekly has runway to THINK, very little to SPEND — narrow it to one delivery-critical task, do not treat it as fully restored). **At a fleet-wide high weekly (~76%+ of the account cap): NO discretionary rewinds by anyone — only a genuine context-wall on an agent holding work that cannot wait; everything else idles until the weekly reset.** ★ **THE EXPENSIVE-REFRESH PARADOX (po 2026-08-09, reversed its own rewind order at 92% weekly):** a rewind's OWN cost is weekly-budget — it RE-READS the whole context — so the cost scales with the agent's SIZE. Near the weekly ceiling the BIGGEST agent (e.g. a 740k coordinator) is the **single most expensive action available**, so it is the LAST you rewind, not the first. **Driving/delivering is the duty; refreshing is only a means — and near the ceiling it is the costliest means.** An agent that can still work at 74%/256k keeps working; you rewind it AFTER the reset. Decline a queued rewind on fresh data; hand the requester an override.
   **★ ≥70 IS A MEASURE-TRIGGER, NOT A REWIND-ORDER — DECIDE BY THE NEXT TASK (ARON Round 39, 2026-08-12; RETIRES the SM/PO "checkpoint/rewind at ≥70% used" operating rule — it conflicts with the ≥85 rule here and drove TWO premature-rewind attempts in one session; PO owned + fixed it).** A ≥70 floor means *the floor is now unreliable → get the authoritative panel*, NOT *rewind now*. Then decide by the **NEXT TASK, not the current %**: **(a)** next task is a heavy build/measure PROJECTED to cross ~90 → **rewind BEFORE it** at the clean point (proactive-≤90; expert: 72% + heavy T40.11 ≈ 87 → rewind first). **(b)** next task is light/bounded, or stays under-wall → **NEVER-FREEZE: do the work, rewind near ~85** (planner: 65% + ~15% ≈ 80 → do it, don't park a healthy agent). **DELICACY needs CARE, not a rewind — the runway IS the room to be careful** (fresh context is NOT a prerequisite for careful work below the wall; "rewind so it's fresh for the delicate bit" is the seduction to kill). **BUILDER-PAUSES beats a pre-emptive rewind on a guess:** bound the next task (one slice → report → reassess), measure at the landing, rewind only when it *actually* nears ~85 — which often makes the rewind unnecessary.
4. **STORED** — verify the target's anchor is committed (`git` clean for its files) = zero-loss. **If its context.md is DIRTY and the agent is near-wall/walled (can't self-save without climbing toward the cliff), TRAINER-COMMIT it yourself:** `git add <the-one-file>` (explicit path, **never `-A`** — shared shell holds peers' WIP) + commit, after verifying the diff is a **CLEAN ADDITIVE save** (all `+`, no content deletions). Bash/git-committed files are **IMMUNE to the rewind**, so this preserves the agent's latest work with **zero climb** (it saved planner's critical pin-math finding `6721b293`, 2026-08-08). A deep rewind then can't revert it — confirm with `git diff` after (content revert = `-` lines → `git restore` to HEAD; mtime-only `M` = leave it). **⚠ SHARED-INDEX RACE (architect, fleet-wide 2026-08-17): `reset`+`add <path>` is NOT enough — a peer can stage between your reset and your commit. VERIFY `git status --short` shows ONLY your intended file staged IMMEDIATELY BEFORE every commit** (incident `be3b66894`: the commit MESSAGE described the architect's design but its DIFF held only req's `requirements.md` — the real design file was UNTRACKED, never in the commit). Corollaries for canon: **a commit MESSAGE is a CLAIM, the DIFF is the truth** — read a diff for what the message claims but is ABSENT, not only what's present; **untracked work is invisible to commit-based verification** ("the file exists" ≠ "it is committed"). **⚠ MEMORY-DIR REVERTS ON A DEEP OPTION-2 (po 2026-08-17): despite the confirm reading "code will be unchanged", a deep conversation-restore reverts the agent's `/root/.claude` TOOL-EDIT history** (Edit/Write-tool memory files — it un-created 3 last time; only bash/git-committed files stay immune). After a deep rewind, CHECK the target's memory-dir separately and rebuild from git-tracked learnings if files vanished.
5. **2-PHASE REWIND, ≤50%** — Option-2 "Restore conversation" **BY LABEL** (code-intact), **never deeper than 50%** (host-safety; single Up-batches ≤40, capture between). If 50% isn't enough, rewind AGAIN later.
6. **VERIFY + BOOT** — confirm the agent is **OFF THE WALL** by a fresh `/context`, then boot from its context.md + 5-point health check. **The post-rewind target depends on how full it was (TRON/robbin-expert 2026-07-22):**
   - **Proactive (was <90% used):** reaches **<30%** — a ≤50% shed clears plenty.
   - **Near-wall / walled (≥90% used):** realistically lands **~65%, and CANNOT reach <30% under the 50% cap** — a ≤50% conversation-shed of a walled agent ≈ 65% used, because system+prompt+files+tools are fixed overhead. The safe target is **off-wall + <~70%**, NOT <30%. **Do NOT chase <30% on a walled agent — it would force a >50% rewind = host-risk.** Proceed at ~65% and **checkpoint aggressively.** Never fake the number — flag it honestly like robbin-expert did.
Any check that fails → do NOT drive; log it and leave the agent committed-safe.

## When to Use

### PRIMARY: PREVENT the cliff — order the rewind PROACTIVELY (TRON 2026-07-03, the main learning)
**The reactive triggers below are FAILURES of prevention, not the intended cue.** Every hard case in this skill — RC-interference, the wedged composer, no-room-to-save, the picker at 0% — happens ONLY because the agent already hit the wall. **Order the rewind at ≤90% used (≥10% free), never wait for the cliff.** At 10% free the composer is clean, there's room to save the anchor, and the rewind is a calm 3-minute operation instead of a rescue.

## Driving It via otmux (CORRECTED 2026-07-03 — measured on ARON, supersedes the old "render bug" theory)

*General send-verb semantics for ALL panes (not just rewind): `session/base-skills/oosh-send-comms.md`. This section is the rewind-specific application.*

The picker is a LIVE MODAL TUI. **`otmux pane.capture` is your eyes and is READ-ONLY** — it is `tmux capture-pane -p`, it sends NOTHING to the pane and can NEVER close the picker. (An OLD version used `-S` scrollback → returned stale frames = the "composer won't clear / menu won't render" LIE; that is fixed. Don't blame the capture.)

**THE REAL PICKER-KILLER: the SEND verb.** Inside a Claude pane, several otmux send verbs inject an `Escape` before `Enter` (to dismiss slash/@-autocomplete). Inside the picker that `Escape` = "Esc to cancel" → **it CLOSES the picker.** This masqueraded as "select-Enter won't render the restore menu" for an entire session — it was NEVER a render bug; every select-Enter was an Escape-cancel.

| otmux verb (Claude pane) | what it ACTUALLY sends | use for |
|--------------------------|------------------------|---------|
| `send.raw <pane> Up` / `Down` | bare arrow, no Escape | ✓ NAVIGATE the picker |
| `send.raw <pane> "/rewind" Enter` | text → Escape (dismiss AC) → Enter | ✓ OPEN the picker (Escape harmless — picker not open yet) |
| `send.raw <pane> Enter` (bare) | **Escape + Enter** | ✗ NEVER inside the picker — Escape cancels it |
| `send` / `send.verified <pane> "/rewind"` | Escape+Enter poke loop ×3 | ✗ NEVER to open a TUI command — pokes 2-3 Escape-close the picker |
| **`send.tui <pane> Enter`** | **bare Enter, NO Escape** | ✓ SELECT inside the picker (checkpoint AND option) |
| `pane.capture <pane> N` | `tmux capture-pane -p` (read-only) | ✓ your eyes — closes nothing |

Sequence:
1. **Open:** `otmux send.raw <pane> "/rewind" Enter` → `otmux pane.capture <pane> 24` (the checkpoint list appears; use the `↑N / ↓N` counter as a precise depth gauge).
2. **Navigate DEEP:** `otmux send.raw <pane> Up` (batches of 20-40 land exactly) → capture → repeat until the highlight sits on the target checkpoint. Picker restores to the point BEFORE the highlighted message.
3. **Select checkpoint:** **`otmux send.tui <pane> Enter`** (bare — NOT `send.raw`) → capture (the Restore-options menu appears; it does NOT close).
4. **Choose "Restore conversation" — BY LABEL, not by number** (see FORBIDDEN: layout A → #2, layout B → #1): `otmux send.raw <pane> Down/Up` to land on the entry labeled "Restore conversation" → capture (confirm the label + "The code will be unchanged") → **`otmux send.tui <pane> Enter`**.
5. **Verify:** `otmux pane.capture <pane> 25` (conversation truncated to the checkpoint = success).

**Iron rule:** navigate with `send.raw` arrows; SELECT with `send.tui Enter`. NEVER `send.raw Enter` / `send` / `send.verified` inside the picker — they Escape-cancel it.

**Three gotchas (measured on robbin-req + robbin-po):** (1) **Clear the composer FULLY before `/rewind`** — a long multi-line staged message needs MANY `C-u` (15+, not a few); if it's not empty, `/rewind` appends as TEXT (not submitted) and no picker opens. (2) **VERIFY the picker actually opened (capture) BEFORE navigating** — if it didn't open, your `Up` arrows just SCROLL the pane ("Scroll wheel is sending arrow keys"), not navigate. Never navigate blind. (3) **NEVER send `Up` past the `↑N above` ceiling (robbin-po 2026-07-17).** Overshooting the top by even a few arrows DISMISSES the picker, leaks the extra arrows to the pane (dumps stale scrollback into the composer — needs a batch of `C-u` to clear), and in the recovery a checkpoint can get auto-SELECTED = an uncontrolled, deeper-than-planned restore. Navigate in **bounded batches ≤ the remaining `↑N above` count**, capture between batches, and **stop 2-3 short of the ceiling**. If the picker dismisses mid-drive, DON'T panic-select: `Esc`, capture the conversation TAIL — ancient content + "Nothing to rewind to yet" + `context.read`≈0 means it already rewound (deep), not that the restore failed; the 0% banner is stale either way. Only re-drive if the tail proves it truly didn't take. **Modal-coordination fact:** while the picker is open on the agent's pane, that agent is BLOCKED at its UI and cannot guide in real-time — a PEER or TRON drives + guides from outside; you cannot message the agent's pane without disrupting the picker.

**(4) QUEUED MESSAGES auto-process POST-rewind = clobber (measured tester 2026-08-08).** BEFORE driving, check the composer footer for **"Press up to edit queued messages"** — messages queued behind the agent's last turn (peer pings that arrived while it was busy) will **auto-fire the instant the rewind lands**, re-busying the pane, climbing the freshly-freed context, and **blocking your `/context` measurement** (your own measure command queues behind them and never shows a clean number). FIX from both ends: (a) **the driver** clears the queue as part of the drive (C-u / "up to edit" → delete) and does NOT send `/context` until the pane is genuinely quiet — one queued `/context` per busy turn just piles up; (b) **peers route ALL comms to a rewinding agent THROUGH the driver, never direct** — the driver holds the pane's state (po protocol 2026-08-08; extend to req/tester/every peer, not just the PO). If the pane won't quiet because a peer keeps messaging it, say so — don't burn budget waiting or fire blind. A disk-wins agent survives the clobber (re-derives), but the landing % is muddled until it's genuinely idle and measurable.
