The instant Tron states a requirement — in chat directly, or relayed by the research
agent (iphone:0.0) — route it to the req agent to capture as a `requirement:uuid` with
his LITERAL quote, BEFORE doing anything else with it. Tron's directive: "let the req
agent note and trace ALL my requirements."

**Why:** Tron asked for a "traceability browser similar to the file browser, with item
view and list views." I captured the traceability UUID-*standard* + remediation sprint
from that same directive, but never routed the BROWSER FEATURE requirement to req. It was
traced nowhere; later "traceability browser under docs" got mis-built as a static matrix
markdown link instead of the interactive browser he specified. Tron: "where is my original
literal requirements… you relayed my reqs in this chat." A requirement that isn't routed
to req on arrival gets half-interpreted and lost — the exact failure the traceability
initiative exists to prevent, and embarrassingly it was the requirement about traceability.

**How to apply:**
1. On EVERY Tron requirement, first action = send it to req with the literal quote to
   capture + trace. Don't split a multi-part directive and capture only the part I acted on.
2. A multi-part directive (e.g. "standard + remediation + browser") = MULTIPLE requirements
   — route ALL parts to req, not just the one I find easiest.
3. "Build/link the doc" is NOT the same as "build the feature" — match what he asked for
   (a browser UI ≠ a markdown link). When unsure, capture literally + ask, don't reinterpret.
