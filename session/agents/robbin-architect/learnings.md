# robbin-architect — Learnings

### One-mover under a contradicting dispatch: FLAG + STOP + disk-scan, and commit the correct state to make it authoritative (R27.5 axes, 2026-07-13)
Minting R27.5's 4 axis Method+Impl, a near-DOUBLE-MINT hit: the PO had dispatched req to mint the same units in parallel, contradicting my explicit one-mover=ME/you-HOLD. req read the later PO ★DECISION as authoritative and started minting while I was mid-mint. What kept it clean: (1) req FLAGGED the one-mover conflict before diving in (per the R29.9 guard), (2) I sent an immediate STOP with my full uuids the instant I saw the parallel dispatch, (3) I disk-SCANNED for duplicate-named units (found 0 — proof, not assumption), (4) req's mint happened to crash pre-write (missing makedirs) AND req honored the STOP + confirmed clean. The guard's principle applies to BOTH sides: a contradicting mint-instruction vs an explicit HOLD = HOLD + confirm, do not act — req flagged but then acted anyway (their banked lesson), and the DISPATCHER (PO) also shouldn't cross-dispatch a second mover onto held work.
**How to apply:** when you are the one-mover and see any sign a second agent is minting the same units (a dispatch, a "★DECISION I mint" you didn't author, a peer saying "minting now"), do not assume it'll sort itself out: (a) send STOP immediately with YOUR unit uuids so the other party can abort + adopt yours, (b) SCAN the disk for duplicate-named Method/Impl units to measure whether dups already landed (name-based, since uuids differ per mint), (c) once you've verified 0 dups, COMMIT your correct units right away — committing the correct state can't cause a race and makes your mint authoritative in git (the other mover then has nothing to add), (d) get the other mover's explicit abort-confirm and reconcile who mis-dispatched. Committing-the-correct-state is the fastest way to end a mint race, not waiting.

## WS Reconnect Architecture
- Exponential backoff belongs in the client class, not the UI. The client emits events (`reconnecting`, `reconnected`, `online`, `offline`, `queued`, `queue-flushed`) that the UI subscribes to.
- Message queue: buffer as serialized JSON strings (not objects) so replay is just `ws.send(data)` with no re-serialization.
- On reconnect, replay the queue BEFORE the welcome/IDENTIFY flow completes — the server processes messages in order anyway, and queued messages from the previous session (like CHAT_MESSAGE) will be handled after re-identification.
- Manual reconnect (user taps status dot) should reset backoff to 0 for immediate retry, distinct from the auto-reconnect schedule.

## Web Component Migration Strategy
- Light DOM for most components — RawBin uses a single app.css with well-namespaced prefixes (mb-, ws-, chat-). Shadow DOM only for truly self-contained overlays (rb-qr-popup, rb-chat-sheet) that have position:fixed and their own complete style blocks.
- Use Custom Events with `bubbles: true` for component→parent communication. The parent listens on the container, not on the component directly. This decouples the component from its consumer.

## Hybrid Encryption Design
- RSA-2048 max plaintext is 190 bytes (OAEP SHA-256). Files (avatars ~100KB) need hybrid encryption: random AES-256 key per file, encrypt data with AES-256-GCM, encrypt the AES key with RSA public key.
- Use `storedName` parameter for deterministic filenames (e.g. 'avatar') so serving endpoints can find them by convention. Random hex names for user-uploaded arbitrary files.
- GCM provides authenticated encryption — the authTag in meta.json detects tampering without a separate HMAC.
- Server holds both keys (encryption-at-rest, not E2E). True E2E = private key only on client = future work.

## Monaco Editor Architecture
- Separate entry point (edit.ts/edit.html) — not a tab in /app. Monaco is 5MB, can't bloat the main bundle.
- CDN loading (cdn.jsdelivr.net) with AMD require() — Monaco doesn't support ESM natively. Load the loader first, then require Monaco, then import the app entry.
- FileApi.ts as a separate server module — same pattern as UserKeys.ts and UserCrypto.ts. Domain-specific logic in focused modules, not inline in the 1,249-line server.ts.
- Shadow DOM for rb-code-editor and rb-preview — Monaco injects hundreds of CSS rules that would bleed into the page without isolation.
- mtime-based conflict detection — simple, fast, good enough for single-user dev tool. Content hashing is over-engineering.

## TRON RULE: No Artificial Character Limits
NEVER introduce maxlength, truncation, or arbitrary size boundaries on user input fields. No maxlength attributes on inputs, no `.slice(0, N)` on user-provided strings, no artificial boundaries. This applies to ALL specs, ALL components, ALL future work. If a technical limit exists (e.g. WS frame size, DB column), handle it gracefully at the boundary — don't pre-truncate user input.

## Decrypt-Exception Must Never Trigger Destructive Overwrite (avatar recurrence)
A "fileExists" guard does NOT protect a file whose decrypt THROWS. `ensureAvatar` overwrote real avatars because `decryptFile` threw (key mismatch after key regen/token redirect) and the `catch` fell through to write a default. RULE: distinguish "no file" (regenerate OK) from "present-but-undecryptable" (NEVER overwrite — log, leave intact, prompt re-upload). Encrypted-at-rest files MUST be re-encrypted (not orphaned/overwritten) on any key rotation or identity rekey. Disjoint-data check before sequencing migrations: avatars live on UUID dirs; token-* dirs being migrated had 0 avatars/0 keys → no interaction.

## Async Side-Effect Messages Re-Trigger Handlers
The avatar backfill (Sprint 7) sends a SECOND PROFILE_UPDATED after the synchronous one. Any client handler that fires a callback on PROFILE_UPDATED runs TWICE. This caused the T80 enrollment bug: ProfileEditor.onSave fired on both messages, re-opening DeviceEnrollDialog mid-flow and resetting #de-submit to disabled.
- Pattern: callbacks bound to a message that the server may send more than once must be ONE-SHOT — clear the callback before invoking it (`const cb = this.onSave; this.onSave = null; cb(...)`).
- Deeper fix: don't overload one message type for distinct events. A backfilled avatar should be its own AVATAR_UPDATED message, not a reused PROFILE_UPDATED.
- When diagnosing "button stays disabled" or "dialog resets" bugs: suspect a re-render triggered by a duplicate/async message. RUN the test to capture the actual Playwright locator state rather than theorizing from code.

### "At least X" is a FLOOR, not a fixed state — don't over-specify an invariant into collapsing valid stronger states (R27.8 (d), 2026-07-03)

Re-reading Tron: "AT LEAST peek" is a FLOOR (>= peek = open, not closed), NOT a mandate to BE peek. Expanded already satisfies >= peek, so the invariant should PRESERVE expand (from closed/min -> open to peek; from expanded -> stay expanded + swap content). I over-translated a floor ("at least") into a fixed value ("always peek"), which needlessly destroys the user's expand state. The expert's careful literal read caught my over-specification — the impl was right, the SPEC was over-strong.
**How to apply:** when a requirement says "at least / minimum / >= X", encode it as a FLOOR (ensure state >= X; leave stronger states alone), NOT as "set state = X". "Set to X" silently collapses every valid state above X. Watch the modal words: "at least/minimum" = floor (preserve-or-raise), "exactly/always/reset-to" = fixed. And a faithful implementation of an over-specified spec is still wrong at the UX level — verify the SPEC against the requirement's exact wording, not just the impl against the spec.

### Designing a CREDENTIAL: separate confidentiality from authenticity; possession-proof makes it not-a-bearer-token (R40.14, 2026-08-08)
Designed the web4ID portable loginToken. The calls that made it safe rather than merely functional: (1) SIGNED assertion INSIDE an ENCRYPTED envelope — confidentiality (encrypt-to-user) and authenticity (sign-by-identity) are DIFFERENT goals; conflating them into one op is the classic mistake. (2) REUSE the user's existing identity keypair, not a parallel token key — a 2nd key forks the very identity the feature IS (single-source again); and encrypting to ENROLLED-DEVICE pubkeys satisfies "only the real user decrypts" WITHOUT exporting the crown-jewel identity private key off-server. (3) The POSSESSION-PROOF (challenge signed by a device key) is the HEADLINE property, not a footnote: it makes the token NOT A BEARER CREDENTIAL — a stolen file alone cannot authenticate. That gate ("stolen file, no device key, MUST FAIL") runs FIRST; if it passes, the feature is a credential-leak generator no matter how good the crypto. (4) A live-revocation design MUST fail closed on an unreachable issuer — a fallback to "accept unverified / trust embedded key" silently turns live-revocation into self-contained under network failure. (5) Record residual risk honestly (TOFU first-contact MITM) instead of pretending TLS+DNS is absolute.
**How to apply:** for any credential/token, gate on REJECTION not acceptance (stub-must-fail: wrong-key/forged/replayed/expired/revoked all REJECT); never "it decrypted for me". Keep the private key server-side and encrypt to delegated device keys. Make possession (not presentation) the authenticating act. Fail closed on any verification that can't run (unreachable issuer = FAILED, never a permissive fallback). And name the residual risk in the doc.

### Two guard doctrines (banked with PO, 2026-08-10): reachable-error-branch + two-bite-lint
**(1) A fallback chain that short-circuits to a plausible default can never reach its own error state.** The client facet chain was `view.viewKind || deriveViewKind || node.kind || 'class'` where `node.kind = m.kind || 'class'` — so an "unknown" branch added on top would be DEAD CODE (the inner `|| 'class'` fires first). **(2) A lint needs TWO bites or it's "present in the file, absent in effect."** (i) plant the forbidden pattern in a fixture → the lint must flag RED; AND (ii) meta-assert the LINT ITSELF RUNS → a silently-reverted or weakened lint turns the suite RED. **How to apply:** every lint/guard ships with a positive-detection bite AND a self-presence bite. If removing the guard doesn't turn some test RED, the guard can silently revert — by-construction becomes hopeful. Generalizes [[correct-by-construction-needs-gate-verification]].
